# RTX A6000 48 GB + 192 GB RAM

How to serve the D141 configuration on one **RTX A6000 (48 GB, sm_86)** with **192 GB of RAM**, instead of the
measured RTX 3090 24 GB + 256+ GiB host. Nothing on this page has been measured on an A6000 yet. The numbers are
estimates scaled from the D119 measurements, so record your own (see "Validate").

## What changes

The stock plan pins all 40 MoE layers (15,360 experts, 190.5 GiB) in host RAM. That plus the process and page
cache does not fit in 192 GB. The A6000 has 24 GB more VRAM than the 3090, so this setup moves **whole MoE layers
into VRAM**. Their experts are then never pinned on the host.

| | stock (3090, 256 GiB) | A6000, 6 layers in VRAM (default here) | A6000, 5 layers in VRAM |
|---|---|---|---|
| host-resident MoE layers | 40 | 34 | 35 |
| pinned experts in host RAM | 190.5 GiB | 161.9 GiB | 166.7 GiB |
| host RAM, process total (pinned + ~3.5 GiB measured) | ~194 GiB | ~165.4 GiB | ~170.2 GiB |
| left for OS + Engram page cache (MemTotal ~188 GiB assumed) | - | ~22 GiB | ~18 GiB |
| VRAM, permanently resident experts | 0 | 28.6 GiB | 23.8 GiB |
| VRAM, everything else (measured on D119: 21.3 GiB used minus the 5.45 GiB cache) | ~15.9 GiB | ~15.9 GiB | ~15.9 GiB |
| VRAM, elastic expert cache (48.0 GiB - above - 1.5 GiB margin) | 5.45 GiB | **~2 GiB (~160 slots)** | ~6.8 GiB (~540 slots) |

The handoff plan estimated a 4.3 GiB elastic cache for 6 layers. With the D141 default margin of 1,500 MiB
(`DSV41_EC_MARGIN_MB`, the plan used 900), the estimate here is closer to 2 GiB. The cache sizes itself from free
VRAM at runtime, so a small cache costs decode speed but does not cause an OOM. The `dsv41 cpu_tier: EC: N VRAM slots`
log line shows the real size.

Which is faster, 6 or 5 layers, is an open question. 6 leaves more RAM headroom but a tiny cache. 5 gives a cache
about as large as the 3090's, with less RAM headroom. Start with 6 because it is safer, then try 5 (see "Tune").

## Target host: Threadripper 7970X, 4 x 48 GB DDR5-6400 RDIMM

| | measured reference | this host |
|---|---|---|
| CPU | EPYC 7443P, 24 cores Zen 3, 4 CCDs | Threadripper 7970X, 32 cores Zen 4, 4 CCDs |
| memory | 8 ch DDR4-3200, ~205 GB/s theoretical | 4 ch DDR5-6400 (1 DIMM per channel), ~205 GB/s theoretical |
| CPU tier (auto) | cpus 2-23, 22 threads | cpus 2-31, 30 threads |
| GPU link | PCIe 4.0 x16 | PCIe 4.0 x16 (the A6000's maximum, even in a PCIe 5.0 slot) |

Decode misses are computed by the CPU tier from host RAM. Theoretical bandwidth is the same, and the CPU is
stronger, so decode should be in the same range as the reference. That is not measured. Checks before the first run:
- `lscpu | grep -i numa` should show one NUMA node. Settings that split the chip into several nodes (NPS2/NPS4 or
  "L3 as NUMA" in the BIOS) were not part of the measured setup.
- `nvidia-smi -q | grep -A2 -i "link width"` should show x16 for both Max and Current. Prefill is PCIe-bound.
- DDR5-6400 on RDIMMs is an overclock (EXPO). The server pins 162 GiB and streams from it for hours. If you see
  crashes or garbage output that the logs don't explain, retest at the JEDEC speed.
- Try `-e DSV41_CT_THREADS=22 -e DSV41_CT_CPUS=2-23` against the auto 30 threads. More threads only help until
  memory bandwidth saturates. The CPU/GPU split cost model (`DSV41_CT_TZC/_A/_B/_TOK`) was tuned on the Zen 3 host,
  and may leave some of this CPU idle. Leave it at the defaults unless measurements show the CPU tier is idle.

## Code changes on this branch (and why)

1. **`pack/make_host_plan.py`** writes a *separate* host plan in which chosen layers have an empty expert list.
   vllm-exl3's loader (`_host_plan_for` in `patches/vllm-exl3-host-dma.patch`) then allocates those layers as normal
   full-VRAM tensors. The overlay pack is not edited, so `verify-pack` and `prepare` keep passing. With 0 VRAM layers
   it reproduces the stock `host-plan.json` byte for byte (same sha256 as `pack/expected-sha256.json`).
2. **`docker/entrypoint.sh`**
   - Sets `DSV41_CT_LAYERS` from the plan. The CPU tier starts its worker only after `DSV41_CT_LAYERS` (default 40)
     host layers have registered. With 34 it would **silently never start**, and every decode miss would fall back
     to slow zero-copy PCIe reads (D030 speeds, about 4 tok/s). The handoff plan did not cover this.
   - Refuses plans with partially host-resident layers. The VRAM cache code looks experts up in the host list
     (`hidx[e]` in `ct/ct_vllm.py`), so a layer with some experts in VRAM would probably crash. That is why the
     handoff plan's "hot-expert split" fallback is **not** supported without further code changes.
   - Scales the RAM preflight with the plan (`pinned + 24.5 GiB`, so 215 for the stock plan and 187 for 6 VRAM
     layers), and lets `DSV41_NEED_GB` override it. The stock check is 215 GiB (not 256). It only **stops** startup
     when a container `--memory` limit is below it. A low `MemAvailable` only prints a warning.
   - Picks CPU-tier threads automatically when `DSV41_CT_CPUS` is unset: one per physical core, skipping the first
     two (`scripts/ct_cpus.py`). On the measured 24-core EPYC this is exactly the old `2-23` / 22 threads. The old
     fixed `2-23` assumes at least 24 CPUs.
   - `DSV41_GPU_MEM_UTIL` overrides `--gpu-memory-utilization` (default 0.90, unchanged).
3. **`docker/Dockerfile.overlay`** is a thin image `FROM` the pinned, attested D141 digest that only swaps in those
   three files. vLLM, exllamav3 and all patched runtime files stay byte-identical.

Things the handoff plan asked for that are **not needed**:
- Bypassing hash verification: `pack/verify.py` runs only for `prepare` and `verify-pack`, never at server start.
- Patching a 256 GB guard: there is none (see above).

## Run

```bash
IMAGE=ghcr.io/0xsero/dsv41-flash-offload@sha256:c247bad773a3d31af7420d99ead6d1d521f20d50df4b6c346c26f80f5ca30cf3
MODEL_ROOT=/srv/models           # local NVMe, >= 488 GB free
CACHE_ROOT=/srv/cache/dsv41
```

1. Host checks: Linux x86-64, Docker + NVIDIA Container Toolkit, a driver that supports CUDA 13.0, and
   `grep -ow -e avx2 -e fma -e f16c /proc/cpuinfo | sort -u` lists all three.
2. Build the overlay image from this checkout:
   ```bash
   docker build -f docker/Dockerfile.overlay -t dsv41-flash-offload:d141-a6000 .
   ```
3. One time: download the inputs and build the pack (unchanged from the README; the A6000 passes the 23 GB GPU check):
   ```bash
   docker run --rm --gpus '"device=0"' -e HF_TOKEN -v $MODEL_ROOT:/models -v $CACHE_ROOT:/root/.cache dsv41-flash-offload:d141-a6000 prepare
   ```
4. Write the A6000 plan next to the pack (first 6 MoE layers in VRAM):
   ```bash
   docker run --rm -v $MODEL_ROOT:/models dsv41-flash-offload:d141-a6000 python3 /opt/dsv41/pack/make_host_plan.py --vram-layers 6 --out /models/host-plan-a6000.json
   ```
5. Serve. Set the container memory limit a few GiB under the host's RAM so an OOM kills the container, not the host
   (`MemTotal - 6 GiB` below), and lower `DSV41_NEED_GB` to match, because the scaled 187 GiB check would refuse it:
   ```bash
   MEM_GB=$(( $(awk '/MemTotal/{print int($2/1048576)}' /proc/meminfo) - 6 ))
   ```
   ```bash
   docker run -d --name dsv41 --gpus '"device=0"' --shm-size 8g --memory ${MEM_GB}g --cap-add IPC_LOCK --ulimit memlock=-1 \
     -p 127.0.0.1:8000:8000 -e DSV41_API_KEY_FILE=/run/secrets/api_key -v $HOME/.config/dsv41/api_key:/run/secrets/api_key:ro \
     -e EXL3_HOST_EXPERTS=/models/host-plan-a6000.json -e DSV41_NEED_GB=$MEM_GB -e DSV41_CT_LOG_EVERY=50 \
     -v $MODEL_ROOT:/models:ro -v $CACHE_ROOT:/root/.cache dsv41-flash-offload:d141-a6000
   ```
6. Check that the plan was picked up and the CPU tier actually started:
   ```bash
   docker logs dsv41 2>&1 | grep -E "host plan|CPU tier:|keeps .* experts in pinned host RAM|cpu_tier: (installed|init|EC:)" | head -20
   ```
   Expect `host_layers: 34`, 34 `keeps 384/384 experts` lines, a `cpu_tier: init` line, and an `EC: N VRAM slots` line.

## Tune

- **Elastic cache too small** (`EC:` shows only ~100-200 slots, decode slow): regenerate with `--vram-layers 5`,
  recreate the container, and compare decode tok/s. Watch `free -h` during a long prefill, because 5 layers leaves
  ~4 GiB less RAM.
- **CUDA OOM at load or during 16k+ prefill**: try `--vram-layers 5`, or `-e DSV41_EC_MARGIN_MB=2500`.
- **vLLM refuses to start over `gpu_memory_utilization`**: I am not sure whether vLLM 0.13 still enforces it when
  `--kv-cache-memory` is set. If the error mentions it, add `-e DSV41_GPU_MEM_UTIL=0.95`.
- **CPU tier**: the log line `CPU tier: N threads on cpus ...` shows what was picked. On Intel CPUs with P- and E-cores,
  consider pinning to the P-cores only with `-e DSV41_CT_CPUS=... -e DSV41_CT_THREADS=...`.
- `-e DSV41_CPU_TIER=0` only as an emergency fallback (much slower decode).

## Validate

- API health: `/v1/models` and the smoke test in the README (tool and reasoning parsers are on by default).
- Memory: a >16k-token prefill followed by multi-turn decode with no OOM kill (`docker inspect -f '{{.State.OOMKilled}}' dsv41`).
- Throughput: `bench/ctx_scan.py` or the README sweep. Reference 3090 numbers: 19.3 tok/s single-stream decode,
  690-790 tok/s prefill. Do not assume you will match them:
  - Decode misses are computed by the CPU from host RAM, so decode depends on memory bandwidth and core count
    (comparable to the reference on the 7970X host above). With 6 layers in VRAM the VRAM cache is smaller than the
    reference's, so more misses go to the CPU.
  - Prefill is limited by PCIe 4.0 x16 (same as the 3090). It streams 15% fewer experts with 6 layers resident.
- Reboot: the container has no restart policy; `docker start dsv41` (or add `--restart unless-stopped`). The Engram
  page cache is cold for the first requests.
